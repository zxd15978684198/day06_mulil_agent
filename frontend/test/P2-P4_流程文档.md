## 2. 四个关键设计决定（都不是随手写的）

### 2.1 只写相对路径 `/api/...`

`api.ts` 里没有任何主机名。dev 期由 Vite 代理转发到 `127.0.0.1:8000`，构建后同源。这样 `D4` 与「不改 CORS」同时成立，前端代码里也没有需要随环境改的常量。

### 2.2 游标越界时**回退到 0，而不是夹到长度**

`sliceNewTrace(trace, cursor)`：

```ts
const safeCursor =
  Number.isFinite(cursor) && cursor >= 0 && cursor <= all.length ? Math.floor(cursor) : 0
```

游标越界意味着"这条轨迹跟记下来的游标不是同一段"（换了会话、后端重启、localStorage 被手改）。此时夹到 `all.length` 会得到**空数组** —— 用户看到的是"这一轮 agent 什么都没干"这种**安静的错误**；回退到 0 最坏只是多显示几条历史，而"多显示"是**可见的、可诊断的**。宁可见、不静默。

### 2.3 `agent_tool_result.content` 解析失败必须兜底

实测该字段是**一个 JSON 字符串**（不是对象）：

```json
"{\"agent\": \"employee_service_agent\", \"answer\": \"申请已提交成功 ✅\\n\\n| 项目 | ...\", \"business_tools\": [\"list_requestable_devices\", \"create_device_request\"]}"
```

内层业务 Tool 名埋在字符串里，必须 `JSON.parse` 才拿得到。而 `answer` 是**模型生成的 Markdown**，完全可能被截断成非法 JSON。所以 `parseToolResult()` 解析失败时**不抛异常**，把整段原样放进 `raw` 交给渲染层折叠展示 —— 解析失败最多是"这一条不好看"，绝不允许变成白屏。

### 2.4 `pending` 必须校验 `action`，不能用 `?? null` 糊

这条是**验证时抓出来的真 bug**（见 §4）。

## 4. 跑通过程中抓到的真 bug

**现象**：36 项里 `非对象 pending 收敛成 null` **FAIL**。

**原因**：`session.ts` 里写的是

```ts
pending: (parsed.pending as Confirmation | null) ?? null,
```

`??` 只对 `null`/`undefined` 生效 —— `'x' ?? null` 会**原样返回 `'x'`**。于是一个被写坏的 `pending: "x"` 会一路漏到渲染层，P7 的模板分派拿到一个字符串，轻则空白卡片，重则抛错整页崩。

**修法**：新增 `coercePending()`，判据是"**必须有一个非空字符串 `action`**"：

```ts
function coercePending(value: unknown): Confirmation | null {
  if (value === null || typeof value !== 'object' || Array.isArray(value)) return null
  const action = (value as { action?: unknown }).action
  if (typeof action !== 'string' || action === '') return null
  return value as Confirmation
}
```

这个判据正好落在契约 `C2` 上（`action` 是模板分派的**唯一**依据）：没有 `action` 的载荷渲染层本来就无法分派，留着它只会变成一张空白卡片，不如直接当它不存在。

修完复跑：**36 passed, 0 failed**。
