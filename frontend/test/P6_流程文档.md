## 2. 四个关键设计决定

### 2.1 轨迹必须**游标切片**，这是本阶段的全部理由

`trace` 是**线程累计**的（契约 C1）。实测三轮：`0 条 → 1 条 → 2 条`，且第三轮的前 1 条与前一轮**逐字相同**。所以任何"每轮把返回的 trace 追加进去"的写法，第 N 轮就会出现 N 份重复（坑 `K1`）。

前端实现：会话里存 `traceCursor`，每轮只渲染 `sliceNewTrace(reply.trace, cursor).fresh`，并把 `nextCursor` 写回。
**关键细节**：中断轮（`answer` 为 null）也**必须推进游标** —— 否则下一轮会把这一轮的条目再渲染一遍。

### 2.2 空轨迹**不渲染面板**

像"你好"这种不触发 Agent 调用的轮次，`trace` 是空数组。渲染一个"调用了 0 个 Agent Tool"的空盒子只会违背"平时安静"的目标，所以 `TracePanel` 在 `entries.length === 0` 时直接 `return null`。

### 2.3 中断轮**没有气泡，但有面板**

`answer` 为 `null` 那一轮（坑 `K8`）不该出现空气泡。但它的轨迹恰恰解释了"确认卡片为什么会弹出来"，所以 `MessageBubble` 的规则是：**文本为空时只渲染 `TracePanel`**。

### 2.4 消息也要持久化（对计划的一处刻意越界）

计划 `L0-S5` 只要求持久化"会话与未决确认"。但如果只存游标不存消息，刷新后会出现"游标在、消息没了"的割裂 —— 面板会显示一段没有对应回答的轨迹。

所以新增 `lib/history.ts` 把**当前会话**的消息一起存下来。这**不是**历史会话管理（`L0-S2` 排除的是多会话列表/历史检索），而是 `L0-S5`「刷新可续」的应有之义。

刻意**不**把它塞进 `session.ts`：那会改动 P3 的交付物，并让 `test/logic-check.ts` 里那 36 条断言失效。

## 4. 跑通过程中抓到的三个真问题

### 4.1 `TEXT_COLLAPSE_CHARS` 声明未使用（`tsc` 拦住）

首跑 `npx tsc -b` 报 `TS6133`。原实现只用了 JSON 那组阈值，纯文本那组没接上。
修法：`const charLimit = mono ? JSON_COLLAPSE_CHARS : TEXT_COLLAPSE_CHARS`，并让行数阈值只对 JSON 生效。
**顺带说明一处对参考值的刻意偏离**：agent-chat-ui 的 `generic-interrupt.tsx` 里字符串折叠阈值是 100 字符，这里放宽到 **400** —— "内层回答"是专家写的一段 1000+ 字符的 Markdown，100 字符会让每一条都要点两次；而它在轨迹面板里本就是次要信息（完整回答已在主气泡）。

### 4.2 React 重复 key（控制台 17 条 error）

```
Encountered two children with the same key, `search_company_knowledge`.
```

原因：专家在一次回答里把**同一个**业务 Tool 调用了 5 次，`business_tools` 数组里就有 5 个同名项；摘要行做了去重，但 `agent_tool_result` 那一行的徽章是**直接 `map`**，于是渲染出 5 个同 key 的 chip。
修法：渲染前统一 `dedupe()`，与摘要行口径一致。修完控制台 0 error。

### 4.3 一次真实的 503 事故 —— 以及它为什么难查（**这是本阶段最有价值的发现**）

**现象**：浏览器发"公司的年假是怎么规定的？"，`POST /api/chat` 连续返回 **503**，前端按设计撤回了乐观消息并弹出错误条；但**同一句话在进程内直接调用却完全正常**（`trace_len = 2`）。

**排查过程**（5 步）：先怀疑前端 → 排除；再怀疑网关瞬时抖动 → 重试仍 503；再在进程内复现两轮对话 → 成功；再怀疑"非主线程首次打开 Chroma" → **停掉后端后三种模式（线程首开 / 主线程首开 / 先主后线）全部成功**，排除线程假设；最后用真实 API 在**全新后端进程**上跑 → **Q1/Q2/Q3 全部 200**。

**根因**（线程内复现拿到的真实 traceback）：

```
ValueError: Could not connect to tenant default_tenant. Are you sure it exists?
  knowledge_base.py:936 in _open_vector_store
  → langchain_chroma/vectorstores.py:374 in __init__
  → chromadb/api/client.py:650 in _validate_tenant_database
```

即那个**长时间运行的后端进程**已经无法再打开 Chroma 持久化库，于是该进程内**所有检索类问题永久 503**，重启即恢复。

**暴露的两个真缺陷**：

| 编号 | 缺陷 | 影响 |
|---|---|---|
| `N1` | `agent_api.py` 的 `except Exception` 把一切异常压成 `503 agent 调用失败`，**且不打印 traceback**（`raise HTTPException(...) from e` 在 uvicorn 默认日志下看不到链式异常） | 事故现场**零证据**：日志里只有一行 `503 Service Unavailable`。这次排查有 4 步纯粹是在猜，因为服务端什么都没说 |
| `N2` | `_open_vector_store()` 的失败**不被缓存也不被重置**：一次打开失败之后，该进程里每次检索都重新走一遍同样的失败路径，**只能重启进程**才能恢复 | 一个瞬时故障会升级成"这个进程从此不能用知识库" |

**处置**：本次**不改**后端（计划 `D6` 只允许 `business_tools.py` 一处改动，且现在处于"连续执行"模式、不宜扩大改动面），已把这两条记入本文档与最终报告，作为**已知限制 / 建议整改项**。运行期的规避办法很直接：**知识类问题返回 503 时，重启后端进程**。

> **补充与更正**（P7 期间的新证据，用来收紧上面的结论）：
>
> - 先前的说法"只有长时间运行的进程才会中招"**不成立**。P7 的取消支路测试里，一个**全新**的后端进程（端口 8032）在**第一次**检索请求上就复现了同一个 `default_tenant` 错误 —— 所以它与进程存活时长无关。
> - "两个进程同时打开同一个 Chroma 持久化库会导致失败"这个假设**已被证伪**：在后端 8000 正在运行、且已成功打开过该库的情况下，另起一个进程去打开它得到 `main-first -> OK`；再把 8000 停掉重开，同样 `OK`。
> - 因此截至 P7 结束，**触发条件仍未定位**。能确认的只有三点事实：① 异常固定是 `ValueError: Could not connect to tenant default_tenant`；② 抛出点是 `_open_vector_store()`；③ 某个进程一旦失败，它后续**所有**检索都会失败（`N2`），**重启该进程即恢复**。
> - 未验证的可疑方向：`src/vector_store/` 下的 SQLite WAL/锁文件残留。可能的来源是验收脚本场景 12 会**整体改名/搬动** `src/vector_store/`，以及本次调试中多次用 `Stop-Process -Force` 强杀持有该库的进程。
> - **运行期建议不变**：知识类问题返回 503 就重启后端进程。

## 5. 偏差声明

| 项 | 说明 |
|---|---|
| **偏差 1** | 消息历史持久化（§2.4）是对 `L0-S5` 的**扩展**，计划原文只要求持久化会话与未决确认。理由与边界已写在 §2.4。 |
| **偏差 2** | 折叠阈值 100 → 400 字符（§4.1）。 |
| **偏差 3** | 本阶段的确认交互只是**临时块**（`ChatView` 内联的 `PendingBlock`）：显示 `action` + 字段预览 + 两个按钮，且已保证 in-flight 禁用。真正的卡片（模板分派、结构化优先 + 通用兜底、防双击）是 **P7** 的交付物。 |
| **未验证** | 未测"知识类问题 503 之后前端能否自行恢复" —— 按当前实现，用户会看到错误条并可以重发，但如果后端进程没重启就会一直失败。这是 `N2` 的表现，不是前端缺陷。 |
| **测试脚本的两处坑（已记录，避免重踩）** | ① 一次 `browser_run_code_unsafe` 里塞三轮模型往返会触发 MCP 调用超时 → 一次调用只做一轮。② **登录页自己也有 `<header>`**，用 `waitForSelector('header')` 判断"登录完成"会立刻返回、读到还没写入的 localStorage → 必须等 `localStorage.getItem(...)` 非空。用这个错误的等待条件曾读出过一次"身份与点击账号不一致"的假象。 |
