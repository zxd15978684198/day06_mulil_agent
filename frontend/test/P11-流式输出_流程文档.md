## 3. 后端 SSE 契约（**实测确认**，不是照抄文档）

`POST /api/chat/stream`（`agent_api.py:276`）→ `StreamingResponse(..., media_type="text/event-stream")`。

| `event` | `data` | 何时发 |
|---|---|---|
| `status` | `{"message": "Agent 已经开始处理"}` | 流一建立就发 |
| `text_delta` | `{"text": "..."}` | 正文增量；**可能是逐 token，也可能是整段一次性** |
| `tool_start` | `{"name": "knowledge_agent", "label": "知识 Agent"}` | Supervisor 派活给某个专家 |
| `tool_end` | 同上 | 专家返回 |
| `tool_error` | `{"name": ..., "label": ..., "message": "… Agent 调用失败"}` | 专家抛异常（**人工确认的 interrupt 也会经由这里**） |
| `confirmation` | interrupt 载荷 | 需要人工确认时 |
| `done` | `{"status": "completed" \| "waiting_confirmation"}` | 流正常收尾 |
| `error` | `{"message": "agent 处理超时，请稍后重试" \| "agent 调用失败，请稍后重试"}` | 流内失败 |

两个必须记住的细节：

1. **`sse_event()` 发的是 `data:{...}`，冒号后没有空格。** SSE 规范说"去掉一个前导空格"，所以解析时必须**只去一个**：去零个会把数据前的字符吃掉，去多个会把正文里的缩进吃掉。
2. **流里没有 `trace`。** 累计轨迹只有 `/api/confirmation` 的 `AgentReply` 才给。所以正常轮次右栏拿不到完整轨迹 —— 这是 `LiveTraceRail` 要 `steps` 兜底的原因（见决定 4）。

## 4. 四个设计决定

### 决定 1：打字机认「全文快照」，不认「增量」

```ts
typer.push(acc)          // acc 是 acc += delta 累积出来的全文
```

`push` 内部只取"比上次收到的更长的那一截"：

```ts
if (snapshot.length <= received.length) return
queued += snapshot.slice(received.length)
```

**为什么**：SSE 的 delta 边界不可靠（可能重复、可能整段一次给），而"快照比已收到的长"这个判据对这两种情况都成立。反过来若把 `acc` 当增量追加，队列会按平方增长 —— 一条 300 字的回答会被吐 300 次第一个字。

**副作用（好事）**：重复投喂同一个快照是幂等的。

### 决定 2：`finish()` 必须**异步**吐完 —— 这里我写错过一次

最初写的是"流一结束就把队列一次放完"，并在注释里给自己的理由是"流结束时队列本来就基本空了，这一下补齐看不出来"。

**真机实测推翻了它**：设备申请这条路上整段回答就是**末尾一条 delta**，而它紧跟着 `done`，于是 `finish()` 把 **100% 的动画**都吞了 —— 浏览器逐 150ms 采样只得到 2 个不同的长度值（23 → 234），一个字都没"打"出来。

现在 `finish()` 返回 `Promise<void>`，让剩余文本继续按帧吐，吐完才 resolve；`ChatView` 要 `await` 它之后再落正式消息，否则那次 `setMessages(finalMessages)` 会把动画中的文本一次性覆盖掉。

### 决定 3：助手气泡抢在第一个 token 之前插入

`send()` 一进来就 `setMessages([...base, 用户消息, 空助手消息])` 并把 `streamingId` 指向后者。

**为什么**：后端要 3～11 秒才吐出第一个字（实测 `tool_start` 在 2.5～3.6 秒、首个 `text_delta` 在 11.2 秒）。这期间若没有气泡，界面就是"发出去了，然后什么都不动"—— 和卡死没有区别。空气泡 + 光标把"活着"这件事表达出来了。

代价是**即使这一轮一个字都没有**（例如设备申请在 interrupt 前没有正文），也要在收尾时把这条空消息删掉 —— 所以 `finalMessages` 的构造条件是 `acc !== '' || fresh.length > 0`。

### 决定 4：轨迹分两路，`trace` 事件优先

后端目前不发 `trace` 事件，所以流式期间右栏只有 agent 级信息。`LiveTraceRail` 的数据源优先级：

1. `entries`（正式轨迹）→ 显示「N 专家 · M 工具」+ 可展开的 `TracePanel`
2. `steps`（实时步骤）→ 显示「↗ 调用 X / ↙ X 已返回 / ！X 调用失败」的竖排列表
3. 都没有 → 一句解释（不是空白）

**如果后端愿意补一个 `trace` 事件**（在 `done` 之前发累计轨迹），前端这边已经准备好了 —— `streamChat` 的 `onTrace` 回调 + `sliceNewTrace` 切片逻辑已接好，改的只是 `agent_api.py`。

## 6. 确定性自检（不依赖后端）

浏览器验证依赖后端，而后端有间歇故障（见 §7）。打字机与帧解析是纯逻辑，所以另做一份 Node 自检：`.tmp/tw_check.cjs`（编译 `sse.ts` / `typewriter.ts` 后用 node 驱动）。

```
PASS  等待 finish() 有实际时长（不再被短路）  — 1265ms

PASS  逐 token 投喂也按帧吐  — distinct=19
PASS  逐 token 投喂的最终长度正确  — 56 / 56

PASS  dispose 会兑现挂着的 finish()  — resolved
PASS  半帧留在 rest 里  — frames=1 rest=20
PASS  补齐后解析出剩余的帧  — frames=2
PASS  frame 事件名与 data 正确
PASS  CRLF 也能切
PASS  没有 data 的帧返回 null
PASS  注释帧返回 null
PASS  data 只去掉一个前导空格  — " two"

```

复现：

```powershell
cd frontend
npx tsc src/lib/typewriter.ts src/lib/sse.ts --outDir ..\.tmp\twbuild --module commonjs --target es2022 --skipLibCheck --moduleResolution node --ignoreConfig
node ..\.tmp\tw_check.cjs
```

## 7. 阻塞：知识类问题现在几乎必挂（**后端缺陷，未修**）

前端流式链路是通的，但**知识类问题拿不到任何 `text_delta`**：知识 Agent 在 30 秒左右抛错，前端收到 `tool_error`，然后一直等到 90 秒超时。

后端 stderr 的根因：

```
File ".../chromadb/api/shared_system_client.py", line 49, in _create_system_if_not_exists
    return cls._identifier_to_system[identifier]
KeyError: 'E:\\projects\\mutil_agent\\src\\vector_store'
...  During task with name 'tools' and id ...
```

这是 chromadb 的**进程级全局字典** `SharedSystemClient._identifier_to_system` 上的竞态：`in` 检查与下标读取之间那个 key 被别的执行流删掉了（同一个 LangGraph 轮次里 `tools` 任务不是单线程跑的）。

**注意它一次都没成功过就不叫"间歇"** —— 实测在**全新进程**上第一次知识查询就挂。这比 P6 文档里记的"偶发"严重得多。缓存在 `knowledge_base._vector_store_cache`：**一次失败就一直是 None**，此后每次调用都重新构造 chroma client，于是每次都踩同一个竞态，直到进程重启。

**建议的修法**（需要你点头，这是后端文件）：

1. **在 `lifespan` 里预热一次向量库** —— 启动时是单线程，构造不会撞竞态，成功后就进了缓存，之后所有请求都命中缓存、根本不再构造 chroma client。这一条就能解决绝大多数情况。
2. 给 `_open_vector_store()` 加一把进程级锁 + 失败重试一次，兜住仍然可能发生的并发首用。

不加这两条：**这台机器上知识类问题基本不可用**，前端做得再对也显示不出字。

## 8. 已知限制

1. **流里没有累计 `trace`** → 正常轮次右栏只有 agent 级信息（决定 4）。
2. **超时是 90 秒且写在 `.env` 里**（`STREAM_TIMEOUT_SECONDS`）。知识问答实测 50 秒以上，一旦叠加 chromadb 竞态就必超时。前端把这句后端文案原样显示。
3. **流中途断开时保留已收到的部分回答**（只挂一条错误提示）。这是有意的 —— 把已经显示出来的正文撤掉只会更让人困惑。但**流都没建立起来**时（401/404/409/503/网络）走的是老逻辑：撤回乐观插入的用户消息并把文字还给输入框。
4. **`tool_error` 在正常的人工确认流程里也会出现** —— 那是 LangGraph 的 `GraphInterrupt` 被 agent 内部的 `except Exception` 接住后先写事件再 re-raise。P11 之前已给 `multi_agent.py` 三处加了 `except GraphInterrupt: raise`，所以现在**不再出现**；这条留作回归说明。
5. **未做虚拟滚动** —— 单会话最多 60 条消息（`history.ts` 的 `MAX_MESSAGES`），暂时不需要。
