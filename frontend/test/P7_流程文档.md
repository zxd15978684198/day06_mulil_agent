## 2. 五个关键设计决定

### 2.1 模板分派**只依据 `action`**（契约 `C2`）

```ts
const action = typeof confirmation.action === 'string' ? confirmation.action : ''
const template = TEMPLATES[action]
const active = template ?? FALLBACK
```

**不许根据字段形状猜类型** —— 猜错会把"审批"渲染成"申请"，比不渲染更糟。两个模板：

| action | 标题 | 展示字段 |
|---|---|---|
| `create_device_request` | 提交设备申请 | 申请人 / 设备 / 数量 / 申请理由 / 预分配编号（读 `payload.candidate`） |
| `approve_device_request` | 审批设备申请 | 申请单号 / 申请人 / 设备 / 数量 / **agent 的决定** / 审批意见 |

### 2.2 按钮语义如实描述后端（契约 `C5` / 决策 `R2`）

后端 `approved` 问的是「**要不要执行 agent 已经决定好的这一步**」，不是「这条申请批不批」。所以：

- 文案是「**确认执行**」/「**取消本次操作**」，绝不写「批准 / 驳回」；
- 卡片**先展示 agent 打算做什么**（模板的 `intent` 一句话）再给按钮；
- 底部常驻一句解释：「确认执行 = 按上面的内容**真正写入**；取消本次操作 = **一个字节都不改**。这里确认的是"要不要执行 agent 已经想好的这一步"，不是"这条申请批不批"。」

### 2.3 未知 `action` 不许白屏（防护断言 `P-3`）

落 `FALLBACK` 模板：不猜语义，只如实陈列原始字段，并给一条显式建议 ——「不认识这个操作类型时，**建议点『取消本次操作』**」。这是"默认拒绝"而不是"默认执行"。

### 2.4 "结构化优先 + 通用兜底"两段式

命中模板时关键字段用表格醒目展示；**无论是否命中**，完整原始字段都收在下面的「原始字段（N 项）」折叠区里。这样即使模板过时了，用户依然能看清自己要批的是什么 —— 这条布局取自 agent-chat-ui 的 `generic-interrupt.tsx#GenericInterruptView`。

### 2.5 防双击是硬要求

`busy` 为真时两个按钮都 `disabled`，确认按钮文案变「处理中…」。理由：`pending_confirmations` 是在**响应返回之后**才被清掉的，两次快速点击会发出两次 `resume` —— 对一个会写盘的动作是真实的数据风险。

> 顺带修了 `coercePending()`：判据从"必须有非空 `action`"放宽成"**有非空 `action` 或有非空 `message`**"。因为契约 `K7` 说后端对"不是字典的中断值"会退化成 `{"message": str(value)}`，这种载荷没有 `action`；若不认它，刷新后卡片会消失、而服务端仍挂着待确认，用户就被 409 锁住却看不到任何按钮。

## 3. 验证证据

### 3.1 卡片渲染（真浏览器）

```json
{
  "pendingAction": "create_device_request",
  "cardTitle": "提交设备申请",
  "cardRows": [
    "申请人 = 张伟",
    "设备 = 24 英寸显示器",
    "数量 = 1",
    "申请理由 = 双屏办公场景：需要一边看需求文档一边写代码，单个屏幕来回切换效率太低，因此需要双屏办公。",
    "预分配编号 = REQ-2026-0021"
  ],
  "buttons": ["确认执行", "取消本次操作"],
  "textareaDisabled": true,
  "placeholder": "请先处理上面的待确认操作"
}
```

注意 `申请人` 与 `设备` 是**中文名**而不是 `USR-001`/`DEV-MONITOR-24` —— 这正是 **P1** 那次后端改动的目的；同时"预分配编号"也说明编号是在 `interrupt` **之前**算好的（避免恢复时算出不同号、重复创建）。

### 3.2 防双击（真浏览器）

点「确认执行」后 400ms 内读到的按钮状态：

```json
[{"text": "处理中…", "disabled": true}, {"text": "取消本次操作", "disabled": true}]
```

随后立刻再点一次 → `secondClickBlocked = "blocked by disabled state (good)"`。

### 3.3 确认支路（真实写盘 + 还原）

| 观测点 | 结果 |
|---|---|
| 中断轮 | `cursor 2 → 3`，`pendingAction = create_device_request` |
| 确认后 | `cursor 4`、`pendingAction = null`、卡片消失、输入框解锁 |
| 消息数与轨迹 | 5 条：`["user:0","assistant:2","user:0","assistant:1","assistant:1"]` —— 中断轮与确认轮各推一条"只有轨迹、没有气泡"的助手消息，符合 `K8` 的设计 |
| 最终回答 | 真实的「申请已提交成功 ✅ … 申请单号 REQ-2026-0021 …」 |
| 数据文件 | `sha16 393e3009b1baf63a → 20c1543397b58274`，`REQ-2026-0021` 存在 |
| 还原 | `restore_ok = True` |

### 3.4 取消支路（**这是先前评审点名的未测盲区，本次首次实测**）

脚本：备份 → 起后端(8032) → 建会话 → 触发中断 → 待确认期间发普通消息 → 取消 → 再发一条 → 还原。

```
1) chat -> 200  needs_confirmation=True  id=REQ-2026-0020
   sha after interrupt = 393e3009b1baf63a   （＝基线，**中断阶段一个字节都没写**）
2) 待确认期间再发普通消息 -> HTTP 409    （K6 成立）
3) 取消本次操作 approved=false -> HTTP 200
   needs_confirmation=False
   answer = 我为你查到了目标设备，但在提交环节的人工确认被取消了，因此这台显示器申请还没有创建。…
4) 取消之后 sha16 = 393e3009b1baf63a   unchanged = True   （P-1 的断言成立）
5) 取消之后再发一条 -> 不再是 409（pending 已被清掉，没有被永久锁死的风险）
```

三条结论：

- **中断阶段零写入**（写盘推迟到确认之后）；
- **取消是真取消**：文件字节级不变，且模型没有"换个说法再问一遍"（先前担心的"取消后再次 interrupt"在本轮没有发生）；
- **取消后 `pending` 被清掉**：第 5 步若还是 409 就说明状态没清、用户会被锁死 —— 实测**不是 409**（该步返回 503，是另一件事，见下）。

> 第 5 步返回的是 **503** 而不是 200：这一条恰好又触发了 P6 记录过的 Chroma `default_tenant` 故障（而且是在一个**全新**进程上，说明与进程存活时长无关）。详见 `P6_流程文档.md` §4.3 的"补充与更正"。它不影响本阶段结论 —— 409 与 503 是两种不同的状态码，能拿到 503 就说明 409 那道闸门已经放开了。

### 3.5 一个有用的业务前置发现

`DEV-MONITOR-24` 的申请要求是「**需说明双屏办公场景**」。用"我原来的显示器坏了"当理由会被员工服务 Agent **正确拒收**并反问补充（`business_tools` 只到 `list_requestable_devices`，不产生 interrupt）。换成双屏办公理由后立刻产生中断。

对前端的含义：**不能假设"用户说申请就一定弹卡片"** —— 必须按 `needs_confirmation` 如实渲染。这一点已被契约 `C2` 覆盖。

## 4. 偏差声明与一处未解释的观测

| 项 | 说明 |
|---|---|
| **一次未解释的 +2** | 那次浏览器运行里，记录数从 19 变成 21（+2），且卡片上的预分配编号是 `REQ-2026-0021`（意味着构建候选时文件里已有 `0020`）。随后做了**受控复测**（API 脚本，起 8031 → chat 触发中断 → confirmation）：`before count=19 maxId=REQ-2026-0019` → chat 后仍 `count=19` → confirm 后 `count=20 maxId=REQ-2026-0020`，**delta = 1**。所以"一次 confirm 恰好写一条"这个机制是确定的，**+2 不是双击造成的重复写入**；浏览器会话期间另有一次性写入没能定位到来源。数据已还原到基线。 |
| **未测** | 自动过期的确认在 UI 上如何表现（后端没有超时机制，本阶段不涉及）。 |
| **未测** | 模板 `approve_device_request` 的**前端渲染**没有用真机走过 —— 它需要 HR 身份 + 一条 pending 申请。该 action 的**后端**载荷已在 P1 验证过（含中文 `applicant_name`/`device_name`），前端渲染走的是与 `create_device_request` 完全相同的模板机制（同一份 `ConfirmationCard`），故未重复。**这是本阶段唯一没有端到端实测的分支**。 |
