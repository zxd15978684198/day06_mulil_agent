# P1 流程文档 · 补齐审批中断载荷

> 阶段目标：让「审批确认卡片」拿得到**人类可读**的申请人姓名与设备名 —— 后端 `approve_device_request` 的 `interrupt()` 载荷原本只有编号（`USR-001` / `DEV-MONITOR-24`），卡片上只能显示编号，HR 看不清"在批谁的东西"。
> 状态：**已跑通**（含一次真实 HR 审批闭环 + 数据还原）。
> 改动范围：**仅 1 处**，`src/personal_assistant/business_tools.py` 的 `approve_device_request`。与计划 `D6`「后端唯一改动」一致。

## 1. 改了什么

`src/personal_assistant/business_tools.py`，`approve_device_request()` 里 `interrupt(payload)` 之前：

```python
# 改前
payload = {
    "action": "approve_device_request",
    "request_id": request_id,
    "decision": decision,
    "comment": comment,
    "applicant_user_id": target.get("applicant_user_id"),
    "device_id": target.get("device_id"),
    "quantity": target.get("quantity"),
}
```

```python
# 改后（P1）
# 仍按稳定编号回源文件解析，不把姓名冗余写进记录 —— 编号才是唯一 join key。
target_view = _request_view(target, _load_users(), _load_devices())
payload = {
    "action": "approve_device_request",
    "request_id": request_id,
    "decision": decision,
    "comment": comment,
    "applicant_user_id": target.get("applicant_user_id"),
    "applicant_name": target_view.get("applicant_name"),  # ← 新增
    "device_id": target.get("device_id"),
    "device_name": target_view.get("device_name"),  # ← 新增
    "quantity": target.get("quantity"),
}
```

**为什么复用 `_request_view` 而不是自己查表**：这个函数本来就是这个文件里"按稳定编号回源文件解析姓名与设备名"的唯一实现（`:271-294`），创建路径 `create_device_request` 也用它（`:562`）。复用它保证两条路径的中文名口径完全一致，也符合 `CLAUDE.md`「ID 是稳定 join key，不要反规范化姓名」的约束。

> 注意：**创建**那条中断载荷（`_build_create_candidate`，`:475-477`）本来就已经带 `applicant_name`/`device_name` 了 —— 实测 `POST /api/chat` 触发创建中断时返回的 `candidate` 里确实有 `"applicant_name": "张伟"`、`"device_name": "24 英寸显示器"`。所以 P1 只缺审批这一处。

## 2. 验证流程与证据

脚本：临时脚本（内联在 pwsh 作业里），端口 8024，收尾自动还原数据文件。

### 2.1 基线

```
baseline sha16=393e3009b1baf63a     （19 条申请，8420 B）
目标申请 REQ-2026-0001  applicant_user=USR-001  device=DEV-MONITOR-24  status=pending
```

### 2.2 第一次尝试：**被权限闸门正确拦住**（重要旁证）

用话术「请审批设备申请 REQ-2026-0001，决定为批准」时，Supervisor 把任务**误路由**给了 `ask_employee_service_agent`（而不是 HR 专家），结果：

```
needs_confirmation=False
trace: ask_employee_service_agent → business_tools: ["query_device_requests"]
```

员工服务 Agent 如实回答：**"我不具备审批权限，也没有任何可以更新申请单审批状态的工具"**，且数据文件 `changed=False`。

这是**第二道权限闸门生效的实测旁证**：员工服务专家手里根本没有 `approve_device_request`，路由错了也批不动。同时暴露一个真实的路由质量问题：Supervisor 对"审批"意图的首次路由不稳定（见 §4 偏差）。

### 2.3 第二次尝试：命中（话术改为显式声明身份）

话术：`我是 HR，请审批设备申请 REQ-2026-0001，审批决定是批准`

**中断载荷（`needs_confirmation=True`，`action=approve_device_request`）**：

```json
{
  "action": "approve_device_request",
  "request_id": "REQ-2026-0001",
  "decision": "approved",

  "applicant_user_id": "USR-001",
  "applicant_name": "张伟",              ← P1 新增，中文名 ✅
```

**数据侧**：`sha16 393e3009b1baf63a → 051f984a8679a5f3`（**真的落盘了**），随后从备份还原 → `restore_ok=True`。

## 4. 偏差声明与顺带发现

| 项 | 说明 |
|---|---|
| **偏差 1（计划外发现）** | 同一条"审批"意图，话术为「请审批设备申请 X，决定为批准」时被判给了**员工服务**专家；加上"我是 HR"后才路由到 HR 专家。这不是 P1 引入的问题（P1 只加了两个展示字段），而是 **Supervisor 路由稳定性**的既有表现。对前端有直接影响：确认卡片的 `action` 可能根本不会出现 —— 前端不能假设"用户说审批就一定弹审批卡"，必须按 `needs_confirmation` 如实渲染（这一点已被 `C2` 覆盖）。 |
| **偏差 2（残留疑问）** | HR 专家在回复里提到"目前还有 5 条待审批申请（REQ-2026-0006、0007、0010、0015、0017）"。这与"基线 19 条"一致，说明待审批池是共享业务数据、与 `thread_id` 无关。 |
| **未做的** | 没有为这条改动补后端单测。理由：该分支的正确性依赖 LangGraph 的 `interrupt()` 运行期，脱离图无法有意义地单测；本阶段的验证走的是**真实 HTTP 闭环**（比单测更强）。 |

```powershell

POST /api/sessions  {"username":"wang_fang"}          # → role: hr, display_name: 王芳

POST /api/chat      {"session_id":"<sid>","message":"我是 HR，请审批设备申请 REQ-2026-0001，审批决定是批准"}
#    → needs_confirmation=true, confirmation.applicant_name="张伟"
# 4) 确认
POST /api/confirmation {"session_id":"<sid>","approved":true}
# 5) 还原数据文件（务必！）
Copy-Item .tmp/p1_backup2.json src/data/day05_device_requests.json -Force
```
