| 文件 | 改动 |

### 动效的两条原则

1. **极轻**。这套界面的视觉规则是"靠 surface 阶梯与 1px 发丝边框分层"，动效只负责让新内容"出现得顺"，不抢注意力。所以只有两个地方有动效：新消息、待确认卡片 —— 都是"刚刚发生的事"。
2. **尊重 `prefers-reduced-motion`**。两个组件都走 `useReducedMotion()`，打开时 `enter()` 返回空对象，**完全不做动画**。

轨迹面板**刻意不做动画**：它是原生 `<details>/<summary>`，展开收起由浏览器负责，既有过渡也无障碍语义，加 JS 动效只会让它变差。

## 3. `P-3` 实测：两种"前端不认识"的载荷都不白屏

做法：直接往 localStorage 里灌造好的 `pending`，然后刷新页面（不需要后端配合）。

**场景 1 — 未知 action**（模拟后端将来新增了一类操作）：

```json
{ "action": "brand_new_action_v2", "some_field": "值", "nested": { "a": 1 } }
```

结果：`pageAlive: true`，卡片出现，标题 `待确认的操作`，`action` 原样显示为 `brand_new_action_v2`，含"建议点「取消本次操作」"提示，两个按钮都在。

**场景 2 — `K7` 退化形态**：

```json
{ "message": "服务端返回了一段非结构化的说明文本" }
```

结果：`cardShown: true`，同样落到"待确认的操作"模板，提示语与原始字段折叠区都在。这一条同时验证了 `coercePending()` 的放宽 —— 否则刷新后卡片会消失、而服务端仍挂着待确认，用户会被 409 锁死却看不到按钮。

**取向说明**：两处都刻意选择**默认拒绝**（提示"建议点取消"），而不是"默认执行"。对不可识别的写操作，谨慎是唯一正确的默认值。

## 7. 阶段的已知限制（汇总，不重复各阶段细节）

| # | 限制 | 详见 |
|---|---|---|
| 1 | `POST /api/chat` 遇到检索类问题时，后端可能返回 **503** 且**日志里没有 traceback**（`N1`）；某个进程一旦失败，它后续所有检索都会失败，**重启即恢复**（`N2`）。触发条件尚未定位 | `P6_流程文档.md` §4.3 |
| 2 | `agent_api.py:158` 的 `async def confirmation_action` 内同步调用 `agent.resume()`，会阻塞事件循环。**本项目定档"最小实现、不搞并发"，单用户单标签下不可见**，故按 `D6` 未改 | `P0_流程文档.md` §6 已知限制 1 |
| 3 | `create_session` 把一切异常映射成 `401`，网关故障时登录页会显示"账号不可用"（文案已写中性以减轻误导） | `P0_流程文档.md` / `P5_流程文档.md` §3 |
| 4 | 会话只活在 `app.state.sessions` 内存里，后端一重启旧 `session_id` 全失效；前端只能在第一次请求拿到 404 时才发现（`C4`/`K4`） | `P0_流程文档.md` §6 已知限制 2 |
| 5 | `approve_device_request` 的**前端渲染**没有真机走过（需要 HR 身份 + 一条 pending 申请）；后端载荷已在 P1 验证，前端走同一份模板机制 | `P7_流程文档.md` §4 |
| 6 | 单包 ~430 kB 未做代码切分 | 本文档 §5 |
| 7 | 浏览器联调期间观察到一次**未解释的数据文件 +2**（受控复测证明"一次 confirm 恰好写一条"，不是双击所致） | `P7_流程文档.md` §4 |
