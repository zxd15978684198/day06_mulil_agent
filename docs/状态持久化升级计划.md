## §1 需求与现状

### 1.1 业务叙事

新员工助手现在把三样东西放在进程内存：Supervisor 的 LangGraph 状态、运行时会话表、待确认集合。后果按严重度：

1. **重启即丢**：正在等人工确认的设备申请，重启后既查不到待确认、也无法从断点继续——申请人只会看到"没有待确认操作"，而申请可能停在半途。
2. **多副本下 404**：会话表是进程内字典，换一个副本处理同一 `session_id` 直接判"会话不存在"。
3. **没有审计轨道**：业务数据只存最终状态与时间戳，谁在何时把 `pending` 改成 `approved`、中间被拒绝过几次，一律无痕。
4. **内存待确认集合与中断不同步**：该集合是"本进程见过中断"的缓存，与检查点里的真实中断位置可以背离，前端据此拦重复提交并不牢靠。
5. **业务数据全量重写无并发保护**：每次把整份申请列表写回，两个进程同时写即后写覆盖先写。

### 1.2 门禁 1 产出物（编号，供来源列引用）

**痛点**

- `L0-P1`：重启丢会话与待确认中断。
- `L0-P2`：多副本下会话表缺失导致 404。
- `L0-P3`：无审批审计轨道。
- `L0-P4`：内存待确认集合与检查点中断不同步。
- `L0-P5`：业务数据全量重写无并发保护。

**约束**

- `L0-C1`：沿用现成 MySQL（`DATABASE_URL`），不新增数据库产品。
- `L0-C2`：允许新增依赖与本地服务；优先级 A 不丢 > C 审计 > B 多实例。
- `L0-C3`：按 `user_id` 隔离数据；审批轨迹只追加、不改写。
- `L0-C4`：身份只来自 `login_as()`，`RunContext` frozen，聊天内容不得改写身份。
- `L0-C5`：写操作仍走 LangGraph `interrupt()`，恢复必须复用同一 `thread_id`。
- `L0-C6`：本轮只出方案，不改项目文件。

**成功标准**

- `L0-S1`：FastAPI 重启后，旧 `session_id` 能继续对话、能完成未决确认。
- `L0-S2`：业务数据唯一真源是 MySQL；JSON 只读保留、不再被写。
- `L0-S3`：同一 `thread_id` 不被并发执行；重复审批与重复提交都有确定结果。

### 10.3 与计划的偏差（8 条，均有理由）

1. **库名定为 `agent_service`**（计划里写的是沿用现有 `DATABASE_URL`，未点名）—— 用户拍板；本机另有一个**同名库 `agent_app`**（与账号同名、含三张空表、与课件无关），**不碰**。

4. **S8 的审批并发用行锁，而非计划原文的"按受影响行数判成败"**：实现是 `with_for_update()` + 恢复后重读状态（`business_tools.py:634`、`:639-643`），**全程没有 rowcount / `UPDATE … WHERE status='pending'`**。并发安全的目标等价达成，但与计划 §5 S8 的文字不符——原稿漏记，补记在此。
5. **`../src/tests` 从"每次 `asyncio.run()`"改为"一个进程一个长驻事件循环"**：首版按"这些用例用 `InMemorySaver`、没有跨循环状态"的判断，每次调用新建/销毁循环 —— **实测被推翻**：模型客户端的 HTTP 连接池是在第一次 `chat()` 里绑在 **那一个**循环上的，第二次调用即 `RuntimeError: Event loop is closed`，业务验收 20 条里有 5 条因此失败（`[13][5][16][7][10]`）。改成单循环后 `[5]`/`[10]` 转绿。 **这是桥接件的缺陷，不是产品缺陷**（生产路径 CLI / Web 各自只有一个事件循环）。
6. **创建申请的编号改为由 `runtime.tool_call_id` 派生**（原为 `interrupt()` 之前 `uuid4()`）：`interrupt()` 恢复时**整个工具函数从头重跑**，`uuid4()` 会重新摇一次 —— 确认页上显示的编号 ≠ 真正写进库的编号，且"按编号查重"的幂等护栏永远命中不了。现场证据：场景 7 打印「真实申请编号: `None`（未预设 0019）/ 新记录: `{}`」，而那一行其实已经创建（条数 19 → 20）。**这是产品缺陷**，也是本轮唯一由"真跑验收"（而非人工审查/静态审计）发现的实现错误 —— 三个子代理与独立审计都没看出来。

### 改了 4 处（每处都带"为什么"注释）

1. **向量库预热**：新增 `knowledge_base.warm_up_vector_store() -> (ok, detail)`；`_open_vector_store()` 加模块级 `threading.Lock()` + 锁内二次检查。两个入口在启动后各起一个 **daemon 线程**预热（`agent_api.py` 的 `lifespan`、`main.py` 的 `amain()`），日志打 `[预热] 知识库索引就绪：N chunks / Xs`。
   用 daemon 线程而不是 `asyncio.to_thread`：后者占用默认线程池，`asyncio.run` 退出时要等那 23 秒跑完。
2. **三个 Agent Tool 改 async**（`ask_knowledge_agent` / `ask_employee_service_agent` / `ask_hr_agent`）：内部 `app.invoke(` → `await app.ainvoke(`。同步版会在默认线程池里占一条线程跑完整条子图（18.9s）；异步版把等待还给事件循环，别的会话与流式推送不被 head-of-line 阻塞。
3. **两处提示词**：Supervisor 加"拿到 Agent Tool 返回后**直接采用**它的内容（别改写、别复述证据全文）"；知识 Agent 加"回答保持简短（先结论、再编号与标题、最多 5 句）"。
4. 用户第一次问知识库问题**不再叠加那 23s 冷启动**。

### 诚实边界

* `thinking` 关不掉（网关行为）；单次延迟仍在 2.6–36s 波动（共享网关）。**要更快只能换 `MODEL_NAME`——没有擅自换。**
* 5 次串行调用是 Supervisor + Agent-as-Tool 的固有成本；要减少属**架构改动**，不在本次范围。
* 改动后的回归：`acceptance_day06.py --only 3,4`（正是知识链）→ **2/2 PASS / exit 0**；`compileall` 与三模块 import OK；`inspect.iscoroutinefunction(...coroutine) == True`；服务重启后 `[预热] 知识库索引就绪` 正常打出。
  **未重跑全量 20 场景**（耗时长且需真实模型）——若需要"全绿"结论，应重跑 `acceptance_day06.py`。
