## 1. 业务实现叙事

这套系统现在的状态全在**进程内存**里：某个员工登录后与助手的全部对话、以及助手停下来等审批的那个暂停点，都存在一台机器的一块内存里。

由此产生四个业务后果，都已经被需求方认下：

**第一，重启即失忆。** 服务一旦重启或换一个实例，员工看到的是空白会话；更麻烦的是「已经提交了申请、正等人点确认」的状态也一并消失——员工不知道自己的申请还在不在，业务上只能重提一次。

**第二，多副本下互相看不见。** 同一个员工的两次点击落在两个不同的实例上时，第二次会得到「会话不存在」（`agent_api.py:111` 把会话存在进程内字典里）。

**第三，没有审批轨迹。** 现在只有「最终状态」——某个申请号是 approved 还是 rejected —— 但没有「谁在什么时候批的、批之前是什么状态」。事后追责时，能查到的只有结果，没有过程。

**第四，同一条申请可能被批两次。** 前端靠内存里的一张「待确认集合」拦重复提交（`agent_api.py:130`），换实例就拦不住；而写工具的写入路径没有幂等键（`business_tools.py:557`、`:638`）。

方案要让业务上发生的变化是：

- 员工换实例、服务重启之后，**对话与暂停点都还在**，能接着往下走。
- 一条申请从发起到被批，**每一步都留下不可改写的记录**：谁发起的、谁批的、什么时候。
- 同一条申请**只会被批一次**，无论并发多少实例。

## 6. 数据流链与步骤划分依据

**数据流链（一行）**：登录 → 会话归属解析 → 建图（持久 saver）→ 对话推进 → 写工具暂停（interrupt）→ 待办登记 → 人工决定 → 审批落账 → 业务写入 → 恢复执行。

**步骤划分依据 = 该数据流链**（不是复用别的需求的骨架）。链上的每个箭头对应 §8 中的一个 P 步骤；链外的事（业务 JSON 迁移、缓存层）不进步骤。

形状判定的机械判据：把本需求的**必需能力集合**（会话跨重启延续、暂停点跨重启延续、多副本可见、待办幂等、审批可追溯）逐个与候选覆盖度对照——`langgraph-redis` 单仓覆盖前三项，后两项无人覆盖，因此按组合型处理。

## 7. 决策

### 7.1 天花板级（R 级，带意图链）

**`R1` 真源边界——「崩了以后哪些事实必须还在」**
- 要什么：审计与身份事实在 Redis 被清空后仍然完整。
- 备选：① Redis 为真源；② 双写对等（Redis 与 MySQL 互为备份）；③ MySQL 真源、Redis 只放可重建的派生态。
- 权衡：①把不可过期的事实放进带淘汰语义的存储；②要求两套存储达成共识，需要分布式事务或对账循环；③只要求单向可重建，重建脚本可验证（`C4`）。
- 推荐与理由：③。`langgraph-redis` 的 TTL 语义明确（`repo/redis-developer/langgraph-redis:README.md:L266`），不能承载审计。
- 放弃的代价：每条可审计动作多一次 MySQL 写入；必须写一个「从 MySQL 重建 Redis 视图」的脚本（`L0-S3` 的验收点）。

**`R2` 会话归属键——「重启后怎么找回同一个会话」**
- 要什么：员工重新登录后找回自己的会话，且不与他人共用历史。
- 备选：① 客户端持有 `thread_id`；② 服务端维护 `user_id ↔ thread_id` 注册表；③ `thread_id` 直接取 `user_id`。
- 权衡：①要求改前端契约；③会让同一账号的会话历史被写入互不相干的对话（`RunContext` 是按登录身份与部门建的，串历史会污染上下文）。
- 推荐与理由：②。现状 `thread_id` 是服务端 `uuid4()` 生成（`multi_agent.py:395`），注册表是唯一能在不改前端的前提下恢复归属的位置。
- 放弃的代价：多一张表、每次建会话多一次主键查询。

**`R3` 待办幂等键——「同一条申请不能被批两次」**
- 要什么：并发实例下，同一条申请的两次决定只有一次生效。
- 备选：① 内存去重（现状）；② `(thread_id, interrupt_id)` 唯一键；③ 仅用 `request_id` 唯一键。
- 权衡：①换实例即失效；③在「同一申请被重新发起」时无法区分两次待办。
- 推荐与理由：②，并把「只能批一次」落在 `UPDATE ... WHERE status='pending'` 的受影响行数上（受影响 0 行即已被别处处理）。该语义与官方 saver 的幂等写法同源（`repo/langchain-ai/langgraph:libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py:L159`）。
- 放弃的代价：必须从 `__interrupt__` 里稳定取出 `interrupt_id`（`agent_api.py:128`）；若该字段在版本升级中变形，幂等键随之失效。

**`R4` 审计写入时机——「审批事实不能被 TTL 带走」**
- 要什么：审批决定与业务写入要么都生效、要么都不生效。
- 备选：① 只写 Redis checkpoint；② Redis 写完异步补 MySQL；③ 与业务写入放同一 MySQL 事务。
- 权衡：②在补写失败时产生「业务已改、审计没有」的静默缺口。
- 推荐与理由：③。审计行与业务写入同库同事务，失败一起回滚。
- 放弃的代价：写路径耦合；业务 JSON 的**全量覆写**（`business_tools.py:141-147`）会拉长事务窗口 —— 收益是消除静默缺口，代价由该窗口承担。

**`R5` 两条轨道分工——「给审计员看什么、给工程师看什么」**
- 要什么：审计查询不依赖 Redis，技术复盘不依赖 MySQL。
- 备选：① 全部走 `get_state_history`；② 全部走自建审计表；③ 业务事实走审计表、技术复盘走 checkpoint 历史。
- 权衡：①受 TTL 与淘汰影响；②丢失「对话如何推进」的过程视图。
- 推荐与理由：③。`get_state_history` 是图上现成 API（`repo/langchain-ai/langgraph:libs/langgraph/langgraph/pregel/main.py:L1514`）。
- 放弃的代价：两套查询入口，使用方需要知道该问哪一个（写进 §8 的 S6 提示词）。

### 7.2 打包默认项（D 级）

| # | 意图（要什么） | 取值 | 否定的代价 |
|---|---|---|---|
| `D1` | 不让会话与待办被静默回收 | 不设 TTL | Redis 内存持续增长，靠 `maxmemory-policy` 与告警兜底 |
| `D2` | 会话关闭可审计而非物理删除 | `agent_sessions.status` 三态 active/archived/expired | 表只增不减，需归档策略 |
